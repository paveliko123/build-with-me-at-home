The door: who may come in

server/lan.ts → search export function lanGate

Every request from another device stops here first. With no live pass and no open tablet setup, the tablet only gets the "resting" page. This is what "local" means on a shared Wi-Fi: the app decides who on the network it answers.

2

The turn: mask, check, answer

server/journey/routes.ts → search r.post('/turn', then server/journey/guideTurn.ts → export async function guideTurn

The route spends from the pass's limits, then guideTurn hides obvious personal details (maskPersonal), asks the guide and the safety check at the same time, and checks the guide's whole reply before it's shown. The result is saved with commitProject into the family folder.

3

Your Claude, sealed off

server/claude/runner.ts → search export function oneShot and export function cleanEnv

The kid's turn becomes a run of your own claude command: --tools '', --safe-mode, --setting-sources '', an empty working folder, and your Claude settings left out of its environment. It can only talk, never touch the computer. It uses your plan, not an API key.

Local versus hosted: what this project showed

The same idea exists as a hosted website (the original Build With Me). Running it as a local copy changed these things, each one visible in the code:

✅ What local gives you

  • The data stays home. Plain files in the family folder; the app refuses a cloud-synced folder (familyDataDir in server/paths.ts).
  • No accounts, no server bill, no API key. Every Claude call is the parent's own plan (runner.ts). A whole app used about 2–3% of a 5-hour limit (slice 8).
  • Supervision you can see. The parent's window is the on switch, and the Parent area only opens on the laptop (presence.ts, requireParent).
  • Talking stays local too. Speech-to-text runs on the laptop, not in a cloud service.

⚠️ What it costs and limits

  • Setup is the family's job: Node.js, the claude tool and its sign-in, packages, a 250 MB speech model (app/setup-check.mjs).
  • Tablets need a home certificate before the browser lets them use the microphone (server/certs.ts).
  • It only works while the laptop is on and the parent's window is open; updates need a restart (the runtime copy in app/launch.mjs).
  • The home network becomes part of security: other devices, other programs and websites on the same laptop all had to be kept out (lan.ts, auth.ts).
  • Sharing stays at home: no public shelf of kids' apps. And Claude's terms are 18+, so letting kids use it is the parent's decision.

A practice to reuse

Review from several fixed viewpoints, then turn every confirmed finding into a check. Before shipping, three separate read-only reviewers looked at the code as a parent, as an attacker and as a child-safety red team, and then again. The second round found something no test had caught: the personal-detail mask turned "I live in fear because my dad hits me" into "I live in [address]" before the safety check could see it. The finding was confirmed in the code (server/journey/personal.ts), fixed, and kept as a check in scripts/verify-revisions.ts ("the instant mask hides real details but never swallows…").

On another project: give each reviewer one clear point of view and a "read only" rule, check every finding yourself before acting on it, and keep each fix as a test so it can't quietly come back. The same project also showed the opposite need: for an everyday "is it safe to install?" question, a short prompt about serious problems only (the README's) gives a clearer answer than a full audit.

Run it again

Everyday use

Double-click Build With Me on the desktop, or type /build-with-me:start in Claude Code. Keep the window open while the kids use it; closing it stops the app about a minute later.

For changing the code

From the project folder: npm run dev:server and npm run dev:web for a development copy, or npm run release then npm start for the built one. Use a separate data folder (BWM_DATA) so tests never touch the family's files.
